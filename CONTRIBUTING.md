## Getting Started

Before contributing:

1. Read the project's `README.md` to understand its purpose and setup.
2. Review `CODE_OF_CONDUCT.md`.
3. Review `SECURITY.md` before reporting security vulnerabilities.
4. Check existing Issues and Pull Requests to avoid duplicate work.
5. Make sure you understand the part of the project you intend to modify.

If you are unsure about a proposed change, open an Issue to discuss it before investing significant time.

## Types of Contributions

Contributions may include:

- Bug fixes and reliability improvements.
- New features and functionality.
- Performance improvements.
- Documentation corrections and improvements.
- Tests and quality assurance.
- Security improvements.
- Refactoring that improves readability or maintainability.

All contributions are subject to review and approval by the repository owner or authorized maintainers.

## Contribution Requirements

Every contribution must:

- Have a clear purpose related to the project.
- Avoid introducing unnecessary complexity.
- Follow the existing code style and project structure.
- Include relevant documentation when appropriate.
- Avoid breaking existing functionality without an approved reason.
- Respect the project's intellectual property and licensing requirements.
- Comply with the project's security policy and Code of Conduct.

Contributors must only submit code and other materials they have the right to contribute.

The maintainers may reject contributions that do not meet these requirements.

## Reporting Bugs

Before reporting a bug:

1. Check existing Issues for similar reports.
2. Confirm that the issue can be reproduced, if possible.
3. Collect relevant error messages and reproduction steps.

When creating an Issue, include:

- A clear and descriptive title.
- A description of the problem.
- Steps to reproduce the issue.
- Expected behavior and actual behavior.
- Relevant logs, screenshots, or error messages.
- Environment and version information when applicable.

Do not include passwords, API keys, access tokens, private keys, or other sensitive information in a public Issue.

**Important:** Do not report undisclosed security vulnerabilities through public Issues. Follow `SECURITY.md` instead.

## Suggesting Features

Feature suggestions are welcome when they provide meaningful value to the project.

A good feature request should explain:

- The problem or need it addresses.
- The proposed functionality.
- Why the feature would benefit the project.
- Possible implementation approaches, if known.

The repository owner and maintainers decide whether a proposed feature fits the project's goals and priorities.

## Submitting Pull Requests

Follow these steps when submitting a Pull Request:

1. Fork the repository, if necessary.
2. Create a separate branch for your change.
3. Make focused, clearly documented changes.
4. Test your changes before submission.
5. Update documentation when necessary.
6. Review your changes for accidental secrets, unrelated modifications, and errors.
7. Push your branch to GitHub.
8. Open a Pull Request against the appropriate branch.
9. Describe what changed, why it changed, and how it was tested.
10. Respond respectfully to feedback from maintainers.

### Pull Request Requirements

Pull Requests should:

- Have a descriptive title.
- Explain the purpose of the changes.
- Reference related Issues when applicable.
- Include testing details.
- Avoid unrelated changes.
- Pass the project's applicable checks.
- Contain no exposed credentials or confidential information.

Submitting a Pull Request does not guarantee that it will be accepted.

Maintainers may request changes, close the Pull Request, or reject it at their discretion.

Do not merge your own changes unless you have the required authorization.

## Code Quality and Security

Contributors are expected to follow secure development practices.

### Code Quality

- Keep code readable and maintainable.
- Use meaningful variable, function, and file names.
- Avoid unnecessary dependencies.
- Add tests when appropriate.
- Remove debugging code that is not intended for production.
- Document non-obvious behavior where useful.

### Security Requirements

- Never commit passwords, API keys, access tokens, private keys, or other secrets.
- Use environment variables or appropriate secret-management tools for sensitive configuration.
- Do not introduce malicious code, backdoors, spyware, or unauthorized data collection.
- Do not weaken security controls without explicit authorization.
- Keep dependencies reasonably up to date.
- Do not access or modify resources without authorization.
- Report potential vulnerabilities privately according to `SECURITY.md`.

If a secret is accidentally committed, notify the maintainers and rotate or revoke the exposed credential immediately. Removing it from the latest commit alone may not remove it from Git history.

Security-related changes may receive additional review before approval.

## Commit Guidelines

Write clear commit messages that explain the purpose of each change.

Examples:

- `fix: resolve application startup error`
- `feat: add configuration validation`
- `docs: update installation instructions`
- `refactor: simplify request handling`
- `test: add validation tests`

These prefixes are recommendations unless the project explicitly requires a particular commit format.

Avoid vague messages such as:

- `changes`
- `update`
- `fix stuff`
- `final version`

Keep commits focused on logically related changes.

## Code of Conduct

All contributors must follow `CODE_OF_CONDUCT.md`.

Harassment, threats, doxxing, malicious behavior, retaliation, deliberate disruption, and other prohibited conduct may result in enforcement action.

Contributors are expected to communicate respectfully and cooperate with reasonable project requirements.

## Enforcement and Permanent Bans

The repository owner and authorized maintainers have broad discretion to manage participation in the project.

### Immediate Permanent Bans

Serious misconduct may result in an immediate permanent ban without prior warning.

Examples include:

- Harassment, threats, discrimination, or targeted abuse.
- Doxxing or unauthorized disclosure of private information.
- Malicious attacks, sabotage, or deliberate damage to the project.
- Unauthorized access attempts or deliberate security breaches.
- Introducing malicious code or attempting to steal credentials or data.
- Retaliating against people who report misconduct.
- Repeated or severe violations of project rules.

### Owner and Maintainer Discretion

**The repository owner and authorized maintainers reserve the right to permanently ban any individual from participating in the project at their discretion, with or without prior warning.**

This discretion may be exercised when a person's behavior, actions, attitude, continued participation, or relationship with the project is considered undesirable or incompatible with the project's interests.

This includes circumstances in which the owner or a maintainer personally dislikes an individual or no longer wishes to work with them.

A ban does not require a prior warning, a progressive disciplinary process, or proof of a security violation when the decision is made under this discretionary rule.

Maintainers may also reject contributions, close Pull Requests, remove inappropriate content, and restrict access to project-controlled resources where authorized.

Enforcement decisions are generally final within the project. The owner or maintainers may choose to review an appeal, but reinstatement is not guaranteed.

All enforcement remains subject to applicable GitHub policies and platform controls.

## Final Notes

By submitting contributions, you acknowledge that you are expected to follow these guidelines, `CODE_OF_CONDUCT.md`, and `SECURITY.md`.

The repository owner and authorized maintainers retain responsibility for deciding which contributions are accepted and who may participate in the project.

Thank you for helping improve **Secret-FF-Doomsday-Project**.
